## Phase Goal

**As a** merchant, **I want to** create a protected identity, bind my wallet, and manage my canonical catalog on real infrastructure, **so that** everything downstream (publication, checkout, settlement) operates on authoritative, encrypted-at-rest domain state.

(Story source: REQUIREMENTS.md MERC-01/CAT-01/CAT-02, Phase 2 goal criterion 1, first half.)

<objective>
Stand up the production `infinitemarkets` LNbits extension inside this repository (D-03): the host-discoverable package skeleton, extension database with `m001` migrations for the merchant/catalog/outbox-intent schema subset, versioned key custody and field-level crypto, the merchant domain service (identity, wallet binding, activation state, relays, notifications config), the full catalog domain (catalogs, products, collections, shipping, drafts, soft-delete), deterministic unsigned event builders, and the §5.1/§5.2 admin JSON API — all behind the extension-owned origin/CSRF/auth guard, on the pinned host.

This plan produces no buyer-facing surface and no relay publication worker — outbox rows are enqueued transactionally here and published by plan 02-02; orders/payments land in plan 02-03. The Phase 1 harness (`make verify`) must stay green throughout (D-05).

Purpose: every later capability (NIP-99 publication, checkout, order admin) reads/writes these tables and services; landing the domain and custody layer first with real-loader evidence removes the highest-risk host-convention unknowns (install path, migration runner, template resolution, sync-start contract) before feature work depends on them.

Output: the `infinitemarkets/` package, `tests/runtime/` suite, and one admin shell template proving the template-renderer convention.
</objective>
