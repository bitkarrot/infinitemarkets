## Phase Goal

**As a** buyer, **I want to** check out with a server-verified total and receive exactly one invoice I can follow privately, **so that** payment truth comes from LNbits settlement alone; **as a** merchant, **I want** legal order actions and honest notifications driven by that same truth.

(Story source: REQUIREMENTS.md WEB-02/PAY-01/PAY-02/INV-01/ORD-01/NOTF-01, Phase 2 goal criteria 2–4 — backend half.)

<objective>
Build the order/payment backend of Release A: `m002` schema, the §8.1 intake + §8.2 reservation/invoice saga against the real host `create_invoice`, settlement via self-filtered listener + durable external_id reconciliation, reservation expiry, retention pruning, the §8.8 email worker with every enqueue point wired, the §5.3 admin order API and §5.4 public checkout/status/opt-out API — all through real host integration (FakeWallet settles real invoices in tests), with leases/fencing per §10.

This plan is backend-only: no HTML/JS surfaces — A2/A3 buyer UI and B1/B5 admin UI land in 02-04 on top of these APIs. The Phase 1 harness stays green (D-05).

Purpose: this is where "one authoritative inventory, no duplicate invoices, no double allocation, relay delivery never mistaken for payment truth" is proven in production code.

Output: `m002` + fx/orders/checkout/settlement/email services + task registrations + public/admin order APIs + the runtime suites proving the invariants.
</objective>
