# Phase 2 — UI Design Contract

> Visual and interaction contract for Release A — Safe Web Commerce. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Authority order:** `docs/technical-specification.md` is normative on every payment, security, state-machine, routing, and privacy question. `.devin/skills/sketch-findings-infinitemarkets/` (sketch winners: 001-D Adaptive Blend, 002-A Linear Split, 003-D Tiered Controls) is binding on presentation and interaction. This contract never overrides either.

## Color

### 60/30/10 Contract (public surfaces, expressed as theme tokens)

| Role | Token | Warm Market (default) | Clean Minimal | High Contrast | Usage |
|------|-------|----------------------|---------------|---------------|-------|
| Dominant (60%) | `--color-bg` | `#f7f1e8` | `#f4f7f7` | `#0b0f14` | Page background |
| Secondary (30%) | `--color-surface` / `--color-surface-alt` | `#fffaf3` / `#f1e4d3` | `#ffffff` / `#e9efef` | `#141a21` / `#1d2630` | Cards, panels, nav, wells |
| Accent (10%) | `--color-primary` + `--color-on-primary` | `#a34f2a` / `#ffffff` | `#266760` / `#ffffff` | `#ffb000` / `#111111` | Reserved elements below |
| Destructive | `--color-danger` | `#b33a3a` | `#a62f39` | `#ff6b6b` | Destructive actions + exception states only |

Accent (`--color-primary`) reserved for: primary CTA buttons, links, active/selected indicators (order-row left rule, progress-step active, focus outlines where `--color-focus` delegates), and the total's emphasis. `--color-accent` (Warm `#d69a3a` / HC `#63d2ff`) is a secondary highlight for preview banners and decorative flourishes — never on actionable controls.

### Semantic colors — system-controlled, never merchant-editable

`--color-success` `#24705a`/`#1f7255`/`#59e3a7`, `--color-warning` `#b87319`/`#a56613`/`#ffd166`, `--color-info` `#356b8c`/`#286f91`/`#63d2ff`, `--color-danger` (above), `--color-focus` `#225bdb`/`#165dff`/`#ffffff`. Advanced Tokens exposes background/surface/text/border/radius/spacing — semantic and focus tokens are excluded from every tier.

### Dark / light handling

There is no runtime dark-mode toggle. High Contrast is the dark preset (dark bg, light text, near-black `--color-on-primary`). Admin surfaces always render in the host LNbits palette — public theme choice cannot darken or recolor admin.

### WCAG save gates (blocking, spec sketch-003 locked)

1. `--color-text` vs `--color-bg` and vs `--color-surface`: ≥ 4.5:1 — block save on failure, show the failing pair and computed ratio.
2. `--color-primary` vs `--color-on-primary`: ≥ 4.5:1 — block save.
3. `--color-focus` must remain a visible, valid token — block save.
4. Semantic colors are not editable; any payload attempting to set them is rejected.
5. Live preview recomputes contrast on every edit, before save — color controls without live contrast feedback are forbidden.

**Copy rules (hard constraints):**

- Never render secrets, nsec, key material, bearer tokens, full payment hashes, or complete BOLT11 in admin UI text. Buyer invoice view shows the full BOLT11 (it is the buyer's own payment request); admin technical evidence truncates to `payment_hash` correlation only (spec §16, sketch-002).
- Settlement language is authoritative: "Payment confirmed" appears only after LNbits settlement. Relay ACKs are delivery evidence, never "paid"; a kind-17 receipt is "buyer-claimed" at most (`receipt_verified` is a cosmetic badge).
- Email subjects carry merchant display name + event name only — never buyer PII or internal order ids (spec §8.8).
- Error copy = problem + what happens next. No raw stack traces, codes, or SQL.
- NIP-04 surface (Release C only) must be labeled "legacy / metadata-exposed" — noted here as a boundary so Release A components don't preempt it.
- Remote product images carry a standing disclosure in admin: "Remote image hosts can learn viewer IP and time" (spec §15).
- RFC 9457 `urn:infinitemarkets:*` error codes map to friendly copy: `insufficient-stock` → "Not enough stock available — reduce quantity or choose another item."; `order-expired` → the expired copy above; `rate-limited` → "Too many requests — wait a minute and try again."; `invalid-shipping-destination` → "This item cannot be shipped to the selected destination."

## Surfaces and Component Contracts

### A. Public buyer surfaces (themed, independent documents)

All public pages are standalone HTML documents: `Cache-Control: no-store`, `Referrer-Policy: no-referrer`, restrictive CSP with no third-party scripts, `img-src https:`. Merchant images render HTTPS-only, `referrerpolicy="no-referrer"`, lazy-loaded (spec §5.4/§15).

**A1 — Product page** `GET /infinitemarkets/p/{merchant_pubkey}/{d_tag}` and `GET /infinitemarkets/p/{naddr}` (NIP-89 handler; resolves locally only, renders or redirects to the canonical page — malformed/wrong-kind/foreign naddr → "This product link is not valid here.")

- Layout (Editorial preset, desktop): `.product-layout` grid `minmax(0,1.15fr) minmax(360px,0.85fr)`, gap `clamp(28px,5vw,72px)` — gallery + context left, persistent checkout card right.
- Content: gallery (≤16 images), title, price + currency, availability (`stock` = on_hand − reserved; unlimited shows no count), sanitized markdown description, specs, shipping options, variation selector (variation children of a `variable` parent; invalid combination → inline error, no submit).
- States: available / sold (`nip99_status=sold` or available=0 → "Sold out" chip, buy controls replaced) / hidden (excluded from catalog; direct URL → "This product is not available.") / pre-order (visible, discovery-only — not purchasable in v1, decision 14 → "Pre-order — purchasing opens later.") / not-found / inactive merchant.
- Collection page `GET /public/collections/{pubkey}/{d}` and catalog browse reuse the same card grid; zero-member collections are never publishable so never rendered.

**A2 — Adaptive checkout** `POST /public/checkout` + invoice view (sketch 001-D Adaptive Blend — LOCKED)

- Merchant selects ONE preset — Editorial (rich display + embedded checkout card), Guided (QStepper: 1 Product → 2 Delivery → 3 Pay), Compact (progressive-disclosure single column). Buyers never see a layout chooser.
- **Invariants across all presets (cannot be overridden by layout or theme):** persistent order summary — Items / Shipping / **Total** always visible before invoice creation; identical field set (country select, address iff any item is physical, optional email, `email_opt_in` checkbox "Send transactional updates. No marketing."); identical validation (inline, `aria-live`); identical payment states and security copy.
- Field bounds (spec §15): ≤64 items, qty ≤10,000 (and merchant cap); address required iff physical; `email_opt_in` requires `email` → consent-without-email error "Enter an email to receive order updates, or turn updates off."
- Idempotency: client generates `Idempotency-Key` `[A-Za-z0-9_-]{32,128}` ≥128 random bits once per checkout session and retries with the SAME key; a 409 replay renders the existing order, not a duplicate.
- Invoice state: QR (host vue-qrcode), copyable BOLT11, integer sat amount, decoded-BOLT11 expiry countdown (BOLT11 wins over `RESERVATION_TTL`), "Waiting for payment" status pill, polling `GET /public/order-status` every 5s with `X-Order-Token`. Copy: "Invoice is correlated to this order only. Creating it does not mark the order paid."
- Invoice-state machine on screen: `creating` (skeleton, no QR yet) → `awaiting_payment` (QR + countdown) → `confirmed` (success view + order ref + chronology) | `expired` (expired copy) | `creation_unknown` (payment-uncertain copy — NEVER a second invoice) | `cancelled`.
- No "pay again" affordance after uncertainty; the only recovery is the reconciled status poll or a merchant-issued new checkout.

**A3 — Order status page** `GET /infinitemarkets/order` (spec §5.4/§11.4 — token contract is normative)

- Shareable link: `/infinitemarkets/order#<token>`. On load, JS reads the fragment, immediately `history.replaceState`-removes it, holds the token in memory only, and sends it as `X-Order-Token` on every 5s poll until terminal state. Token NEVER appears in path or query (spec decision 17).
- Renders ONLY: state, shipping_state, total_sat, bolt11, payment status, item summaries, expiry — plus an email opt-out action (`POST /public/order-email-opt-out`). Never merchant internals, internal ids, buyer address/contact echoes, tracking numbers, or other orders' data.
- Buyer-facing state labels: `awaiting_payment` → "Waiting for payment" + invoice block; `confirmed` → "Payment confirmed"; `processing` → "Preparing your order"; `completed` → "Complete"; `cancelled`/`rejected`/`expired` → "This order is no longer active" (+ merchant-visible reason only when public-safe); `payment_exception` → "On hold — the merchant is reviewing a payment issue."
- Dead/invalid/revoked/expired token → "This order link is no longer valid." — identical copy for nonexistent orders (no existence oracle).

### B. Merchant admin surfaces (host-styled, LNbits-consistent — NEVER merchant-themed)

Admin pages mount inside the host shell; density, nav, status colors, and action hierarchy follow LNbits conventions. One sidebar nav section: Orders / Catalog / Publications / Settings (merchant, notifications, appearance).

**B1 — Order workspace** (sketch 002-A Linear Split — LOCKED; UI-02, ORD-01)

- `.workspace` grid `390px minmax(0,1fr)`: searchable/filterable list left, persistent detail right. Selection survives filter/status changes.
- Filters row: search input ("Search order or buyer") + state select (All / Awaiting payment / Confirmed / Needs attention / Expired / Cancelled). Count summary in header ("N active orders · M need attention").
- Order row: reference, channel chip (Web/Gamma/NIP-15), buyer handle (web = email as supplied; protocol = truncated npub), item summary, total in sats, state pill. Active row: `inset 3px 0 var(--color-primary)` left rule + 10% tint.
- Detail pane order (fixed): ① heading (ref, channel, buyer, state pill) → ② exception banner (danger, names the exception + explains) → ③ legal contextual actions ONLY (derived from §7.1/§7.2 — illegal transitions are hidden or disabled with a tooltip reason, never offered) → ④ metrics grid (Total / Payment / Inventory / Protocol) → ⑤ items + fulfillment (address shown decrypted to owner only) → ⑥ chronological `order_events` timeline → ⑦ collapsed "Technical delivery details" (truncated payment_hash correlation, relay ACK evidence — never keys, full BOLT11, or bearer tokens).
- Legal action map: `confirmed` → Start processing / Cancel with reason (reason required, refund warning — "never implies money was returned"); `processing` → Mark shipped (tracking/carrier/eta optional, tracking encrypted) → Mark delivered; `awaiting_payment`/`invoice_pending` → Cancel; `payment_exception` → Accept paid order (oversell/backorder flow disclosed) / Request refund / Confirm refund sent; `expired|cancelled` with settled payment → accept via exception only; terminal → "No legal action" disabled.
- Shipping exception: `exception` reachable from `processing|shipped`; recovery action requires reason, recorded in `order_events`.
- Token rotation: "Reissue status link" (web orders) — revokes old token immediately, shows new link once.
- Mobile (≤560px): list → full detail surface on selection with explicit "← Back to orders".

**B2 — Publication health dashboard** (PUB-02)

- Per-relay table: relay URL, connection state, last positive/negative ACK, pending counts. Relay ACKs labeled "delivery evidence" — never "published = paid" conflation.
- Outbox table (QTable, dense): event kind (0/30402/30405/30406/31989/31990), aggregate ref, state pill (`pending|claimed|publishing|partially_published|failed|superseded`), attempts, per-relay outcome cells, supersession marker. `order_msg` rows never show superseded (spec §7.4) — out of Release-A scope but the cell renderer must not lie.
- States: empty outbox ("No publications pending"), partial (yellow — names the non-ACKed relays), failed (danger + retry affordance), clock-skew publication pause surfaced as a health failure (decision 8).
- Payment exceptions queue surfaced as its own attention list.

**B3 — Catalog management** (CAT-01/02)

- Entities: catalogs, products (simple/variable/variation × digital/physical), collections, shipping options. Each row: title, d_tag, type/format, price, stock (on_hand − reserved; `NULL` → "Unlimited"), visibility pill (on-sale / hidden / pre-order), draft badge, published state.
- Product editor: identity (title ≤200, summary ≤500, description ≤64 KB markdown with allowlist sanitizer), price `(amount_minor, currency, decimals)`, images (≤16, HTTPS-only URLs, no server-side fetch + viewer-IP disclosure), specs, categories, weight/dims, stock (NULL = unlimited), visibility, draft toggle ("Draft — never published in v1"), collections membership (published products MUST belong to ≥1 published collection — publish blocked at zero, spec §6.1), shipping option references + `extra-cost`.
- Variation editor: exactly one `a` parent link; a variation cannot be a parent (depth=1 enforced in UI).
- Shipping editor: title, base price, currency, service (standard/express/overnight/pickup — pickup requires location or geohash), countries (non-empty ISO alpha-2), regions, duration min≤max with H|D|W unit, carrier, weight/dim bounds; `price-distance` is rejected in v1 (spec §6.3).
- Deletion: always soft-delete dialog; when still referenced → reference report OR explicit strip-and-republish (merchant chooses, spec §6.7); removing a collection's last active product offers tombstone-or-replacement in the same flow. Copy carries the no-guarantee disclosure.
- `GET /products/{id}/events` dry-run preview: rendered unsigned event JSON per protocol in a read-only viewer before publish.

**B4 — Merchant settings & identity** (MERC-01)

- Identity card: display name, pubkey (hex, copyable — public key is not secret), profile fields, `payment_preference` fixed "manual" badge (decision 7), `SPEC_REVISION` shown (§12).
- Key actions: generate OR import nsec (masked input, TLS-only note, never echoed/logged); key material never rendered after entry. Wallet binding: LNbits wallet selector, ownership revalidated on write; change blocked while any order is `invoice_pending|awaiting_payment` — disabled control carries that reason.
- Relay config: write/discovery relay list (wss:// normalized), NIP-89 handler pair status.
- Activation state machine `draft → publication_pending → active → deactivating → inactive`: "Publish everything" enqueues republication; "Begin deactivation" runs the two-step flow listing blocking nonterminal orders/exceptions, tombstones commerce + NIP-89 events but NOT kind-0/10050 by default (explicit key-retirement checkbox, spec §6.7). ## Public / Admin Theme Separation Boundary

- Theme tokens are emitted as CSS custom properties scoped under a `.gm-public` root on public documents only. Admin documents never receive the theme stylesheet or the token object.
- No code path may apply merchant theme values to admin surfaces, checkout field order/validation, totals visibility, payment states, focus visibility, or security copy — these are invariants enforced in review and by the contrast/save gates.
- Theme settings persist as a validated token object (`preset`, `brand`, `advanced` — all allowlisted keys); free-form CSS is never stored or rendered (sketch-003).
- Admin uses the host palette and the semantic tokens above for state pills; public uses preset/brand tokens with the same semantic state semantics (success/warning/danger/info meaning is stable across presets).
