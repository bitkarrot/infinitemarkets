## Phase Goal

**As a** merchant, **I want** my catalog to publish to relays with durable per-relay evidence and my storefront to render under my chosen bounded theme, **so that** buyers can discover products through Nostr/NIP-89 while I retain evidence of delivery.

(Story source: REQUIREMENTS.md PUB-01/WEB-01/UI-01/UI-03, Phase 2 goal criteria 1–2 — transport + presentation half. Publication-health *display* lands with the admin UI in 02-04.)

<objective>
Turn the 02-01 domain into a live public storefront and working publication pipeline: the extension-owned nostr-sdk transport with bounded connections, the durable outbox publisher with per-relay ACK evidence and §8.6 ordering, the NIP-89 naddr handler, the standalone themed public documents (product, collection, merchant profile), the §5.4 read-only public JSON, and the theme-token backend with WCAG save gates — per the approved `02-UI-SPEC.md` and sketch findings.

This plan deliberately carries no admin UI and no checkout — B2–B6 admin surfaces and A2/A3 land in 02-04 after the order backend (02-03) exists. The Phase 1 harness stays green (D-05).

Purpose: the outbox is the highest-risk async component (fencing, per-relay evidence, supersession, ordering); landing it with real `LocalRelay` integration before checkout depends on it keeps the vertical slice honest.

Output: `services/transport.py|outbox.py|relay.py|nip89.py|themes.py|tasks.py`, public templates/static, and runtime tests covering transport, headers, themes, and publication evidence.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| public routes -> internet | unauthenticated, rate-limited, read-only catalog data; naddr handler performs no outbound fetch |
| extension -> relays | `send_event_to` results are evidence, not truth; relay URLs restricted to the validated configured set (§9.5) |
| theme tokens -> public documents | validated allowlist only; never admin surfaces; contrast gates enforced server-side |
| worker -> db claims | fenced claim-token CAS; stale workers cannot commit |
| owned Client -> process lifecycle | created with bounded params, closed on stop; raw keys never attach |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-202-01 | Information disclosure | public pages leaking internals | high | mitigate | standalone docs + restricted JSON + tests scanning for secrets/ids |
| T-202-02 | Tampering | forged publication state | high | mitigate | claim_token CAS on every leased write; durable relay_publications reconstruction |
| T-202-03 | Repudiation | lost/misattributed relay evidence | medium | mitigate | verbatim SendEventOutput persisted per copy/relay |
| T-202-04 | Denial of service | relay timeouts stalling claims | medium | mitigate | bounded batches, per-relay failure isolation (OQ6 probe), backoff bounds, bounded client params |
