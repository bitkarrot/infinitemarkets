## Phase Goal

**As a** merchant, **I want to** configure inbox relays and activate Gamma ordering with proof my kind-10050 profile actually reached a relay, **so that** Nostr buyers can discover where to send me wrapped orders — and as the operator I want every inbound connection SSRF-checked and NIP-42-authenticated before any message is trusted.

(Story source: REQUIREMENTS.md GAM-01/GAM-04/GAM-05; Phase 3 goal criteria 1, 4, 5 — the transport/activation half.)

<objective>
Build the Release-B transport foundation end to end: the m006 migration (`peer_relays`, `relay_cursors`, `inbox_blocklist`, `merchants.inbox_state`, `relay_configs` auth columns), keystore `nip17_wrap`/`nip17_unwrap` implementing the qualified §8.5 chain, the kind-10050 publish + reachability gate (pending → active/error) riding the existing outbox evidence machinery, the durable inbox transport (subscribe + admission + EOSE cursors + manual NIP-42 + paid-relay detection), buyer kind-10050 discovery with DNS-egress checks, and the admin APIs that expose all of it.

The leading tracer ships the thinnest complete vertical: admin enable → kind-10050 intent → outbox publish → positive `accepted` evidence → `inbox_state=active` — so the whole activation path is proven on real infrastructure before crypto and subscription depth are layered on.

Purpose: everything else in Phase 3 (order intake, dual-copy replies, sign-in, conformance) consumes this plumbing; the schema additions (peer_relays/relay_cursors per §4.11) were deferred from m002 and MUST land now.

Output: m006, keystore NIP-17 ops, inbox transport + admission + cursors, peer-relay discovery + egress checks, activation admin API, three runtime test suites.
</objective>
