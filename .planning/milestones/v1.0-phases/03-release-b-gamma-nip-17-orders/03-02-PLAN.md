## Phase Goal

**As a** Nostr buyer, **I want** my wrapped kind-16 order to become a real order with a real invoice — priced by the merchant's own catalog — and **I want** payment, status, shipping, and receipt messages to flow back over my declared inbox relays, **so that** a Nostr-native checkout has the same commerce authority as the web one.

(Story source: REQUIREMENTS.md GAM-02/GAM-03/GAM-04; Phase 3 goal criteria 2, 3, 4.)

<objective>
Turn the `received|validated` rows 03-01 admits into the working Gamma order channel: the rumor⇄domain adapter (`order_messages.py`), the full §8.5→§8.1 intake into the canonical checkout/reservation/invoice/settlement services, the `order_msg` dual-copy outbox branch (recipient+sender copies with per-class evidence), inbound type-3/17/14 handling and sender-copy recovery, the rejected-intake + mute surface, no-route retry policy, and the crash-durability drills proving no duplicate domain commands across restarts.

The tracer is the whole economic loop in one slice: golden-constructed type-1 wrap → admitted → unwrapped → order created via shared pricing/inventory → saga to `awaiting_payment` → type-2 payment-request dual-copy published to buyer-inbox and merchant-inbox LocalRelay fixtures with both `delivery_copy` evidence classes — asserting no wrap ever crosses relay sets.

Purpose: this is the phase's center of gravity — every later surface (Messages, sign-in history, conformance) consumes the order/message rows this plan produces.

Output: `order_messages.py`, completed `inbox.py` dispatch, `order_msg` outbox branch, abuse/retention/reconcile extensions, three Wave-0 runtime suites.
</objective>
