## Phase Goal

**As a** merchant-operator, **I want to** prove the exact LNbits/SDK/platform/database profile with reproducible qualification evidence before any production runtime is built, **so that** merchants' real funds are never exposed to an unqualified contract.

(Story source: REQUIREMENTS.md user story "As an operator, I can prove the exact LNbits/SDK/deployment profile before merchants use real funds", adapted to the Phase 1 qualification-harness boundary.)

<objective>
Build the executable state, transaction, fencing, crash, and notification models that prove the database contract of the corrected specification: transaction atomicity, FK behavior, fencing, last-unit concurrency, the cancellation/invoice saga, restart closure, email persistence, and the SMTP boolean boundary (workstream 01-02 from the ROADMAP: "Build executable state, transaction, fencing, crash, and notification models").

These are executable models against the harness's own schema in the extension-database boundary style of spec §14 — they run on the same dialect-switching pytest surface created in plan 01-01, under both SQLite and PostgreSQL profiles (D-03). The LNbits payment boundary is exercised through a documented controllable fake (its real behaviors were qualified in P0-03); the fake replays only the qualified outcome set: success, definitive rejection, timeout/unknown, settlement, and late settlement.

Purpose: The corrected contract's highest-risk silent failures — duplicate invoices after unknown creation, stock released then late-settled, stranded partial publication, SMTP failures marked sent, irrecoverable magic links, and recipient dedupe collisions (see .planning/research/PITFALLS.md) — must fail visibly here, before any runtime code exists to harbor them.

Output: extended harness/schema.py and harness/tx.py, new harness/state.py, harness/saga.py, harness/queues.py, harness/email.py, and five p0-named test modules providing P0-06 through P0-10 evidence recorded in the existing evidence bundle.
</objective>
