## Phase Goal

**As a** buyer on any shop — Nostr inbox or not — **I want** a sign-in affordance that offers the method I actually have and honestly tells me when one is unavailable, **so that** signing in never depends on infrastructure I can't see; **and** once inside, **I want** my profile to show which identities are linked and let me attach the other.

(Story source: Phase 03.1 CONTEXT D-09 surface, D-12, D-13; RESEARCH pitfall 6 render-gate finding.)

<objective>
Ship every buyer-facing surface of the account model: the widened sign-in render gate + two-method modal with per-method availability hints, the email-aware chip/menu/orders page with the 'found N past orders' note, the symmetric profile page (verified email, link cards both directions, kind-0 gating), and the e2e harness (`/_e2e/mailbox` + dummy SMTP env) that proves the whole flow in a real browser without real mail.

Purpose: plans 01–02 built the mechanism; this plan makes it reachable and proves it end to end — the UI is where the no-oracle and honest-degradation postures become visible to buyers.

Output: widened `_store_ctx` flags, extended `public_nostr.js`, `/_e2e/mailbox`, buyer.spec.ts additions.
</objective>

## Trust Boundaries

|| Boundary | Description |
||----------|-------------|
|| API data -> DOM | email strings, npubs, order titles are attacker-influencable render input — GM.h text binding only |
