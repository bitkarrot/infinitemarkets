# Phase 03.1 Research — Buyer accounts: email magic-link sign-in and Nostr identity linking

## User Constraints

Locked decisions copied verbatim from `03.1-CONTEXT.md`:

### Identity model (operator: unified account)
- **D-01:** New `buyer_accounts` table — one row per (merchant, account). Identities: `email_hash` and `pubkey_hash` columns (each nullable, unique-when-present, merchant-scoped HMAC under privacy_key purposes like the existing `PURPOSE_BUYER_PUBKEY`/`PURPOSE_EMAIL_RECIPIENT` patterns).
- **D-02:** `buyer_sessions` gains `account_id`; sessions mint against the account (not the raw identity) so revoke/expiry semantics stay identical to today.
- **D-03:** `orders` gains `buyer_email_hash` (same HMAC index pattern as `buyer_pubkey_hash`); order history for an account = union of pubkey-hash and email-hash bindings. Backfill existing orders by decrypting `contact_enc` (migration or lazy-on-first-verify — planner decides).
- **D-04:** `nostr/claim` unchanged — a claimed private-link order binds to the account.

### Email magic-link sign-in (operator: magic link)
- **D-05:** `POST /api/v1/public/nostr/email/request` — accepts `{email}` (+ `?shop=`), always returns the same "check your email" body (no-oracle — codebase convention, not negotiable). Token is high-entropy, single-use, ~15 min TTL; hash-only persistence (mirror `nostr_challenges`).
- **D-06:** Rate-limit per email + per IP (email-bombing) via the existing `rate_limit_buckets`/`check_public_rate_limit` machinery; tighter than sign-in (e.g. 3/email/hr, 10/IP/min).
- **D-07:** Send via the existing `email_queue` worker — host readiness check `settings.is_email_notifications_configured()` already gates it; magic-link row should carry a clear skip reason like the existing `host-email-unconfigured`.
- **D-08:** Clicking the link (`GET /infinitemarkets/auth/email#<token>` or query — planner picks the least-leaky option consistent with the §5.4 fragment-token contract) verifies + mints the session cookie (same HttpOnly/Secure/SameSite=Strict cookie, same 7-day TTL).

### Order auto-binding (operator: auto-bind on verify)
- **D-09:** On successful email verification, orders with matching `buyer_email_hash` (same merchant) attach to the account — including unclaimed ones. Surface a quiet "we found N past orders" note on the orders page (honest UX, not silent magic).

### Identity linking / merge (operator: prove both, union merge)
- **D-10:** Signed-in account can add the other identity: email → sends a verify link to that email (same token machinery, flag "link-only: prove, don't sign-in"); nostr → NIP-07 challenge round-trip (existing `nostr/challenge`+`verify` pattern, link variant).
- **D-11:** If the verified identity already belongs to another account → union merge: identities and order bindings move to the surviving account, sessions re-point, the other row is retired. Either direction is legal.

### Profile page (operator: email + link-nostr card)
- **D-12:** Email-only accounts see verified email, order prefs, and a "Link a Nostr key" card; the kind-0 editor unlocks once a nostr identity is linked. Nostr accounts get a symmetric "link an email" action.

### UI surface
- **D-13:** Sign-in modal offers both methods: "Sign in with Nostr" (existing flow) + "Email me a sign-in link" (email field + submit). The modal/chip/orders/profile surfaces from this session are the baseline — extend, don't rebuild.

### Posture locked by codebase convention (not questions)
- No-oracle responses everywhere (uniform "check your email" regardless of account existence).
- Encrypted-at-rest PII (email stored `*_enc` like `contact_enc`; HMAC indexes for lookups).
- Exact-Origin + CSRF on mutations; session cookie flags unchanged.
- Bound every user-supplied string; bound email send volume.

### Specifics from CONTEXT (non-decision sections)
- This host has working SMTP (Fastmail via `lnbits_email_notifications_*`) — but the feature MUST degrade honestly when unconfigured (`host-email-unconfigured` skip + UI hint), not silently no-op.
- `INFINITEMARKETS_NSEC_SIGNIN` is the precedent for "dev affordance behind a flag" — magic-link needs no flag but the same restraint applies.
- Orders' contact email lives inside `contact_enc` JSON — backfill decrypts it; new checkouts write `buyer_email_hash` at order creation.

## Architecture Patterns

### Schema (m008 — follow m007 shape, `migrations.py:902-950`)

```
CREATE TABLE {s}buyer_accounts (
    id TEXT PRIMARY KEY,
    merchant_id TEXT NOT NULL REFERENCES {s}merchants(id) ON DELETE RESTRICT,
    email_enc {blob_t},
    email_hash TEXT,
    pubkey_enc {blob_t},
    pubkey_hash TEXT,
    retired_at {int_t},

CREATE UNIQUE INDEX ux_buyer_accounts_email
    ON {s}buyer_accounts(merchant_id, email_hash)

CREATE UNIQUE INDEX ux_buyer_accounts_pubkey
    ON {s}buyer_accounts(merchant_id, pubkey_hash)
    WHERE pubkey_hash IS NOT NULL
```

- **New purpose constant required** [VERIFIED]: `PURPOSE_BUYER_EMAIL = "buyer-email"` in `crypto.py` (add beside `PURPOSE_BUYER_PUBKEY` line 33). CRITICAL: `orders.buyer_email_hash` and `buyer_accounts.email_hash` MUST use the same purpose + `crypto.normalize` so hash equality drives the union lookup. Do NOT reuse `PURPOSE_EMAIL_RECIPIENT` — purposes are domain-separated on purpose (`crypto.py:32-38` docstring).
- New token table mirroring `nostr_challenges` (`migrations.py:920-931`):

- `orders` gains `buyer_email_hash TEXT` + `CREATE INDEX ix_orders_buyer_email ON {s}orders(merchant_id, buyer_email_hash)` — hash only, no enc column needed (the plaintext email already lives in `contact_enc`) [VERIFIED: `checkout.py:836-838`].
- `buyer_sessions` needs `account_id TEXT` AND `buyer_pubkey_hash` relaxed from `NOT NULL` (`migrations.py:940` — currently `TEXT NOT NULL`). **SQLite cannot drop a NOT NULL — the table must be rebuilt** (CREATE new / INSERT SELECT / DROP / RENAME / recreate `ix_buyer_sessions_pubkey`). A rebuild works on both dialects and is the simplest single path. [VERIFIED: m007 DDL; no rebuild precedent exists yet — this is the first column-nullability change.]
- `email_queue` needs a `payload_enc {blob_t}` column so the worker can render the link at send time (see "Magic-link email transport" below).
- **Backfill in the same migration** (recommended over lazy — see Open Risks for why):
  - `orders.buyer_email_hash`: `SELECT id, contact_enc FROM orders WHERE contact_enc IS NOT NULL`, decrypt, `json.loads(...)["email"]`, `hmac_index(privacy_key, "buyer-email", merchant_id, normalize(email))`. The decrypt pattern already exists: `orders.py:504-522` `_customer_email`.
  - `buyer_sessions` → `buyer_accounts`: one account per distinct `(merchant_id, buyer_pubkey_hash)`; `pubkey_hash` copies directly, `pubkey_enc` needs re-encryption with `record_id=<new account id>` (AAD is record-bound — ciphertext cannot be transplanted [VERIFIED: `crypto.py:4-9`]).

### `orders.contact_enc` — email already parseable [VERIFIED]

- Web checkout writes `contact_enc = json.dumps({"email": email, "phone": phone})` (`checkout.py:836-838`, AAD `record_id=order_id, table="orders", column="contact_enc"`).
- Gamma intake writes `{"email": email, "phone": phone, "npub": npub}` (`checkout.py:1553-1556`).
- Both paths pass `payload.get("email")` unvalidated beyond the `email_opt_in`-requires-email check (`checkout.py:719-724`) — values can be `None`/empty/odd-shaped; backfill must tolerate `json.loads` failure and falsy/non-string `email`.
- New checkouts must ALSO write `buyer_email_hash` at insert time in `_insert_order_intake` (`checkout.py:860-900`) and `_insert_gamma_order_intake` (`checkout.py:1575-1611`) when a non-empty email is present.

### Session/account interaction

- `_mint_session` (`nostr_auth.py:355-394`) currently writes `buyer_pubkey_enc`+`buyer_pubkey_hash` per session. Under D-02, mint must instead: get-or-create `buyer_accounts` row by identity hash → `INSERT buyer_sessions(..., account_id, ...)`. Keep writing `buyer_pubkey_*` on the session for nostr sign-ins (cheap compat: `session_from_cookie` and `/nostr/profile` still get `buyer_pubkey` without a join).
- `session_from_cookie` (`nostr_auth.py:428-469`) must return `account_id` and the account's resolved identities; for email-minted sessions `buyer_pubkey_enc` is NULL and the current code returns `None` at line 462 — restructure the dict to `{id, merchant_id, account_id, buyer_pubkey(optional), email(optional), pubkey_hash, email_hash}` and keep the identical-None failure posture.
- Downstream session consumers to update [CITED]:
  - `views_public_api.py:514-522` `/nostr/orders` — `buyer_pubkey_hash = :h` → `(buyer_pubkey_hash = :ph OR buyer_email_hash = :eh)`.
  - `views_public_api.py:653,686,726` `/nostr/profile` — requires `buyer_pubkey`; email-only sessions must fail honestly (uniform 401/422) since there is no key to fetch/sign kind-0 with.
  - `checkout.py:665-670` — attributed checkout pulls `buyer_session["buyer_pubkey"]`; for email-only sessions this is `None` → order binds via `buyer_email_hash` instead (write session-account email_hash, not the form email, so binding is to the *verified* identity).
  - `nostr_auth.claim_order` (`nostr_auth.py:514-580`) — binds `buyer_pubkey_*` with a `IS NULL` CAS. For email-only accounts, bind `buyer_email_hash` symmetrically (extend CAS guard to whichever column the account offers); with both identities, write both.
- **Auto-bind on verify (D-09) needs no order mutation**: once `buyer_email_hash` is written at checkout + backfilled, the union query attaches orders implicitly. The "found N past orders" note is just `SELECT COUNT(*) FROM orders WHERE merchant_id=:m AND buyer_email_hash=:h` at verify time, returned in the response (`bound_orders`).

### Token verification endpoint shape — USE THE FRAGMENT

- [VERIFIED: docs/technical-specification.md:641-647] The §5.4 contract: bearer token arrives ONLY as a URL fragment (`/infinitemarkets/order#<token>`), JS strips it via `history.replaceState`, sends it as `X-Order-Token`. `public_storefront.js:80-100` implements exactly this.
- Query params leak into server access logs, browser history, and any future referrer slips. **Prescription:** magic link = `{public_base_url}/infinitemarkets/auth/email#<token>` (+ optional `?shop=`). New page route `GET /infinitemarkets/auth/email` (same shape as `order_page`, `views.py:482-506`) renders a minimal template; JS strips the fragment and POSTs `{token}` to a verify endpoint which mints the cookie and redirects to `/orders` (or `/profile` on link-flow).
- Verify endpoint: `POST /api/v1/public/nostr/email/verify` — `require_origin` (login-CSRF posture identical to `nostr_verify`, `views_public_api.py:398-408`), single-use CAS `UPDATE ... SET used_at=:n WHERE id=:i AND used_at IS NULL AND expires_at > :n` mirroring `nostr_auth.py:344-351`, identical-401 for every failure class (`SIGNIN_INVALID` reuse is fine).

### Magic-link email transport — `email_queue` needs extension, not bypass

- [VERIFIED: `email.py`/`orders.py:346-424`] `enqueue_email_intents` only knows merchant/customer order events and `event_type` is validated against `EMAIL_EVENT_TYPES` (`orders.py:108-118`). A magic link is **orderless**: `order_id=NULL`, `channel='customer'` would be suppressed with `consent-revoked` (`email.py:159-161` requires `order.email_opt_in` for customer rows), and `UNIQUE(order_id,...)` never dedupes NULL order_ids (no intent dedupe — acceptable, request-side rate limits bound volume).
- **Prescription:** add a third channel (e.g. `'account'`) + event type (e.g. `'signin_link'`) — NOT via `enqueue_email_intents` (it forces merchant+order semantics); write a dedicated `enqueue_magic_link(tx, merchant_id, recipient, link)` mirroring `enqueue_test_send` (`email.py:408-436`): `recipient_enc` AAD `record_id=merchant_id` (orderless precedent — worker already decrypts with `record_id=row["order_id"] or row["merchant_id"]`, `email.py:320-328`), `recipient_hash` via `PURPOSE_EMAIL_RECIPIENT`.
- Worker changes needed [CITED: `email.py`]:
  - `_suppression_reason` (142-162): skip the consent/`notify_events` checks for `channel='account'`; `email-disabled`/`host-email-unconfigured`/`merchant-inactive` still apply — D-07 is satisfied free of charge.
  - `_rate_bucket_ok` branch (294-306): `'account'` rows rate-limit like customer — keyed on `recipient_hash`, its own bucket name + cap.
  - `_subject`/`_render_body` (165-200): branch on `event_type='signin_link'` — subject/body carry the link from `payload_enc` (decrypt `record_id=row["id"], table="email_queue", column="payload_enc"`); never put the token in the subject/logs.
  - `payload_enc` stores `{token}` (or full link) AEAD'd — same posture as `orders.public_token_enc` (encrypted copy retained while valid). This also gives the e2e harness a server-side decrypt path (see Test Surfaces).

### Rate-limit bucket usage [VERIFIED]

- `check_public_rate_limit(request, bucket=..., limit=..., window_s=...)` (`nip89.py:216-245`) — fixed-window `rate_limit_buckets` insert+count, scope = `hmac_index(privacy_key, "rate-limit", "", client_ip)` (merchant-agnostic, IP-only). Per-IP bucket for the request endpoint: `bucket="nostr-email-req", limit=10, window_s=60`.
- Per-email limit needs a custom scope — `check_public_rate_limit` takes no scope override. Follow `_rate_bucket_ok` (`email.py:122-136`): fixed hourly window, `INSERT ... ON CONFLICT DO UPDATE SET count=count+1 ... WHERE count < cap RETURNING count`, scope = the email's `buyer-email` HMAC (never raw address — bucket keys are always hashes).
- Precedent for bucket naming: `nostr-challenge`, `nostr-verify`, `nostr-claim`, `nostr-profile`, `checkout-min`, `checkout-hour`, `public-get`, `public-page`.

### Readiness/SMTP gate + skip vocabulary [VERIFIED]

- `host_settings.is_email_notifications_configured()` per worker tick (`email.py:243-246`); `ext_settings().email_enabled` (`settings.py:149,188` — `INFINITEMARKETS_EMAIL_ENABLED`).
- Suppression vocabulary (`email.py:148-162`): `email-disabled`, `host-email-unconfigured`, `merchant-inactive`, `event-disabled`, `consent-revoked`. Worker outcomes: `sent`, `suppressed`, `rate-deferred`, `retry`, `failed`, `lost_claim`, `error` — metrics via `metrics.incr(f"email.{outcome}")`.
- Honest-degradation UI hint: the email method's availability is a host capability, not a per-account oracle — safe to surface (e.g. an `email_signin` flag on the `/nostr/challenge` response like `nsec_signin` at `views_public_api.py:387`).

## Don't Hand-Roll

- **Do not invent a new session cookie or token format** — reuse `SESSION_COOKIE`/`SESSION_COOKIE_PATH`/`NOSTR_SESSION_TTL_S` (`nostr_auth.py:179-189`) and `crypto.generate_public_token`/`token_lookup_hash`.
- **Do not send email synchronously in the request path** — `email_queue` + worker is the only send path; SMTP call is always outside the transaction (`email.py:318-350`).
- **Do not build a separate rate-limit table or store raw emails/IPs in buckets** — `rate_limit_buckets` + HMAC scopes only.
- **Do not write `.innerHTML` or string-concatenated DOM in `public_nostr.js`** — `GM.h` only; a static test greps for it.
- **Do not reuse `enqueue_email_intents` for magic links** — it enforces `EMAIL_EVENT_TYPES` membership and merchant-notify semantics; dedicated enqueue mirroring `enqueue_test_send`.
- **Do not add a `nostr/email/verify` GET** — token-in-URL-GET is exactly what the fragment contract exists to prevent.
- **Do not mutate orders on verify** — hash union is the binding; only `order_events` writes are for explicit claim (existing behavior).
- **Do not hand-write ALTER COLUMN for `buyer_sessions.buyer_pubkey_hash`** — rebuild the table (SQLite limitation, first of its kind in this codebase).

## Common Pitfalls

1. **`buyer_sessions.buyer_pubkey_hash` is `NOT NULL`** (`migrations.py:940`) — email-minted sessions have no pubkey. Table rebuild required; forgetting it produces INSERT failures only seen on the email path.
2. **`session_from_cookie` returns `None` when `buyer_pubkey_enc` decrypts empty** (`nostr_auth.py:450-462`) — email sessions would die here if the contract isn't restructured.
3. **AAD is record-bound** — `buyer_pubkey_enc`/`email` ciphertexts cannot be copied between tables/rows; backfill must decrypt-then-re-encrypt under the new `record_id`. Wrong `record_id`/`table`/`column` at decrypt → `CryptoError`.
4. **Customer-channel suppression requires `order.email_opt_in`** (`email.py:159-161`) — an orderless magic-link row on `channel='customer'` is silently suppressed with `consent-revoked`. Use the new channel.
5. **`email_queue` UNIQUE dedupe never fires for `order_id=NULL`** (NULLs distinct on both dialects) — repeated requests enqueue multiple rows; that's fine only because request-side rate limits bound it. Don't rely on queue dedupe.
6. **`nostr_signin` template flag = `inbox_state == 'active'`** (`views.py:135`, `public_base.html:44-54,75`) — the chip/modal/JS simply don't render when the merchant inbox isn't active. Email sign-in is inbox-independent: the flag (or a sibling flag) must be widened, e.g. `inbox_active OR host_email_configured`, else email sign-in is unreachable on draft/off merchants. Planner must decide the render rule and the honest "email unavailable" hint when SMTP is unconfigured.
7. **`check_public_rate_limit` is IP-scoped only** — per-email limiting needs the `_rate_bucket_ok`-style custom-scope pattern; passing the email into `check_public_rate_limit` is not possible without extending it.
8. **Merge identity-column collision**: `buyer_accounts` has ONE `email_hash` + ONE `pubkey_hash` — an account can hold at most one of each. If a signed-in account (email1, pubkey1) verifies an identity belonging to another account that *also* has a populated complementary column, the union cannot be represented in one row. Planner needs an explicit rule (recommend: reject with a uniform honest error — "this identity belongs to a different account that already has both sign-in methods; sign in there instead" — or merge only when the moved identity type is NULL on the survivor). See Open Risks.
9. **`keystore_env` fixture runs migrations by explicit import list** (`conftest.py:262-279`) — add `m008_*` there or schema tests run against a stale schema.
10. **Challenge/verify rate buckets share the shared testclient IP** — runtime tests already `DELETE FROM rate_limit_buckets` to reset (`test_nostr_signin.py:782-786`); new per-email/per-IP buckets will need the same hygiene in tests.
11. **`session_from_cookie` pre-migration rows** — sessions minted before m008 have `account_id=NULL`; keep them working (pubkey path intact) or backfill accounts in the migration (recommended) AND tolerate NULL on read.
12. **Kind-0 profile endpoints assume a pubkey** — `/nostr/profile` GET/POST and `_profile_cache` key on `session["buyer_pubkey"]` (`views_public_api.py:653,686,726`); email-only sessions must be refused before `_fetch_kind0`/`event.author()` comparisons, not crash.

Magic-link request (route shape — mirror `nostr_verify`'s guards):

```python
class EmailRequestBody(_Strict):
    email: str = Field(min_length=3, max_length=254)

@infinitemarkets_public_api_router.post("/nostr/email/request")
@public_boundary
async def nostr_email_request(request, response, body: EmailRequestBody):
    await _guard(request, response)
    await nip89.check_public_rate_limit(
        request, bucket="nostr-email-req", limit=10, window_s=60)
    nostr_auth.require_origin(request)
    merchant = await _merchant_for_signin(request)
    await nostr_auth.request_email_signin(
        merchant["id"], body.email, _client_scope(request))

    return {"sent": True, "detail": "check your email for a sign-in link"}
```

Token verify + account mint (service shape — mirror `verify_signin` CAS):

```python
async def verify_email_token(merchant_id, token, *, settings=None, now=None):
    # token_lookup_hash strict-decodes BEFORE lookup (CryptoError -> 401)
    digest = crypto.token_lookup_hash(token).hex()
    async with DomainTransaction() as tx:
        row = await tx.fetch_one(
            f"SELECT * FROM {tx.table('email_signin_tokens')}"
            " WHERE token_hash = :h AND merchant_id = :m"
            " AND used_at IS NULL AND expires_at > :n",
            {"h": digest, "m": merchant_id, "n": now})
        if row is None:
            raise SIGNIN_INVALID
        rc = await tx.execute(
            f"UPDATE {tx.table('email_signin_tokens')} SET used_at = :n"
            " WHERE id = :i AND used_at IS NULL AND expires_at > :n",
            {"n": now, "i": row["id"]})
        if rc != 1:
            raise SIGNIN_INVALID
        account = await _get_or_create_account_by_email(
            tx, merchant_id, row, settings, now)
        bound = await tx.fetch_one(
            f"SELECT COUNT(*) AS n FROM {tx.table('orders')}"
            " WHERE merchant_id = :m AND buyer_email_hash = :h",
            {"m": merchant_id, "h": account["email_hash"]})
        return await _mint_session(tx, merchant_id, settings, now,
                                   account=account), bound["n"]
```

Email-queue enqueue (mirror `enqueue_test_send`, `email.py:408-436`):

```python
async def enqueue_magic_link(tx, *, merchant_id, recipient, link, now):
    settings = ext_settings(); ver = settings.active_key_version
    row_id = uuid.uuid4().hex
    await tx.execute(
        f"INSERT INTO {tx.table('email_queue')} "
        "(id, merchant_id, order_id, channel, event_type, recipient_enc,"
        " recipient_hash, payload_enc, state, attempts, next_attempt_at,"
        " claim_token, created_at) "
        "VALUES (:i, :m, NULL, 'account', 'signin_link', :re, :rh, :pe,"
        " 'pending', 0, :n, 0, :n)",
        {
            "i": row_id, "m": merchant_id,
            "re": crypto.encrypt(recipient.encode(), settings.master_keys[ver],
                record_id=merchant_id, table="email_queue",
                column="recipient_enc", key_version=ver),
            "rh": crypto.hmac_index(settings.privacy_key,
                crypto.PURPOSE_EMAIL_RECIPIENT, merchant_id,
                crypto.normalize(recipient)),
            "pe": crypto.encrypt(link.encode(), settings.master_keys[ver],
                record_id=row_id, table="email_queue",
                column="payload_enc", key_version=ver),
            "n": now,
        })
```

## Recommended Task Slices

1. **m008 schema + backfill** — `buyer_accounts`, `email_signin_tokens`, `buyer_sessions` rebuild (`account_id`, nullable `buyer_pubkey_hash`), `orders.buyer_email_hash`+index, `email_queue.payload_enc`, backfill orders email-hash + session→account migration; `crypto.PURPOSE_BUYER_EMAIL`; conftest `keystore_env` migration list.
2. **Service layer: accounts + sessions** — `nostr_auth` account get-or-create (both identity types), session mint against account, `session_from_cookie` restructure, NULL-account compat, update `claim_order` for email binding; update `/nostr/orders` union + `/nostr/profile` pubkey-required guards + attributed-checkout binding in `checkout.py`.
3. **Magic-link vertical** — `email_signin_tokens` request/verify service + `POST /nostr/email/request` + `POST /nostr/email/verify` routes, per-email+per-IP rate buckets, `enqueue_magic_link` + worker `channel='account'`/`event_type='signin_link'` branch (suppression, subject/body, rate bucket, payload render), `GET /infinitemarkets/auth/email` page + fragment JS.
4. **Identity linking + merge** — link-token variant (`purpose='link'`, bound `account_id`), NIP-07 link-challenge variant, union-merge service (identity move, sessions re-point, loser `retired_at`), collision rule.
5. **Frontend** — modal two-method UI, chip for email-only accounts, auth landing page, `/orders` "found N past orders" note, `/profile` verified-email card + link cards + kind-0 gating, `public_base.html` signin-flag widening, email-unconfigured UI hint.

## Open Risks

1. **Merge collision rule (biggest unknown):** one `email_hash` + one `pubkey_hash` column per account cannot represent "two emails on one account". D-11 says either direction is legal, but a link where both accounts already have the *same* identity type populated is unrepresentable. Planner must pick: (a) reject with honest copy (recommended — bounded, no silent identity loss), or (b) graduate to a `buyer_identities` child table (bigger scope, deviates from D-01's column wording). Needs an explicit decision before slicing task 4.
2. **Backfill vs lazy (D-03 open question):** recommend **migration-time backfill** — `contact_enc` decrypt is deterministic, the volume is bounded by merchant order counts, lazy-on-verify would still need the same code plus a "did we backfill yet" marker and leaves `/nostr/orders` incomplete for never-verifying users. Migration does it once, honestly. Counter-consideration: very large order tables make the migration slow — it's a sequential decrypt loop; the planner should bound/log it rather than batch-worker it.
3. **Sign-in affordance gating:** `nostr_signin` renders only when `inbox_state=='active'`. Email sign-in must render independent of inbox state — decide whether the email method shows always (with an "email unavailable" hint when `is_email_notifications_configured()` is false) or only when configured. Both are honest; the CONTEXT's "degrade honestly … UI hint" wording favors show-always-with-hint.
4. **Claim semantics for email sessions:** `claim_order` writes `buyer_pubkey_*` with an `IS NULL` CAS keyed on pubkey. For email-only accounts the symmetric write is `buyer_email_hash`; for accounts holding both, write both. The CAS/foreign-bound oracle posture must stay identical (one `CLAIM_INVALID`).
5. **`/nostr/profile` for email-only sessions** — currently assumes `buyer_pubkey`. Decide response shape (e.g. `{email, pubkey: null}` so the chip can render an email initial) vs keeping the endpoint pubkey-shaped and adding account fields. Public API shape leaks "account has email" only to the session owner — fine.
6. **e2e token retrieval:** tokens are hash-only at rest — the harness cannot read them back from `email_signin_tokens`. `payload_enc` on the queue row (or a `token_enc` column on the token table, `orders.public_token_enc` precedent) is required for BOTH the worker's link rendering AND a `/_e2e/mailbox` inspection route. Plan the decrypt path deliberately.
7. **Orderless queue rows never dedupe** — the same email+IP rate limits are the only bound on duplicate magic links (3/hr makes ≤3 duplicate emails/hour possible). Acceptable but worth a comment in code.
8. **`nostr/email/verify` merchant scoping:** tokens are minted per-merchant; a token presented under a different `?shop=` must fail identically (merchant_id in the lookup WHERE clause — mirror `verify_signin`'s `merchant_id` bind).
9. **Multiple merchants sharing one email:** accounts are merchant-scoped — the same email on shop A and shop B yields two accounts. That's per D-01; just don't accidentally global-scope the HMAC (merchant_id is inside `hmac_index` args already).
10. **Session fixation on link-verify:** verify-from-email can land on any device/browser — that's intended (magic link IS the credential). `require_origin` on the POST still applies (JS fetch sends it automatically); do not relax it for the fragment flow.
