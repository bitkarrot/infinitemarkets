# Phase 03.1: Buyer accounts — email magic-link sign-in and Nostr identity linking — Context

**Gathered:** 2026-10-05
**Status:** Ready for planning
**Source:** Informal discuss-phase (operator session)

<domain>
## Phase Boundary

Buyer accounts for the public storefront: buyers without a Nostr signer can register/sign in via **email magic link**; buyers with Nostr keep NIP-07 sign-in. Both are identities on a unified per-shop account. Signed-in buyers see order history (new + auto-bound historical by verified email), claim private links, and link the other identity from the profile page — merging two pre-existing accounts by union.

**Out of scope:** passwords; unlinking an identity; email as a notification preference upgrade (order email opt-in semantics unchanged); admin tooling beyond existing surfaces; any change to anonymous private-link checkout (it stays the primary path).

</domain>

<decisions>
## Implementation Decisions

### Identity model (operator: unified account)
- **D-01:** New `buyer_accounts` table — one row per (merchant, account). Identities: `email_hash` and `pubkey_hash` columns (each nullable, unique-when-present, merchant-scoped HMAC under privacy_key purposes like the existing `PURPOSE_BUYER_PUBKEY`/`PURPOSE_EMAIL_RECIPIENT` patterns).
- **D-02:** `buyer_sessions` gains `account_id`; sessions mint against the account (not the raw identity) so revoke/expiry semantics stay identical to today.
- **D-03:** `orders` gains `buyer_email_hash` (same HMAC index pattern as `buyer_pubkey_hash`); order history for an account = union of pubkey-hash and email-hash bindings. Backfill existing orders by decrypting `contact_enc` (migration or lazy-on-first-verify — planner decides).
- **D-04:** `nostr/claim` unchanged — a claimed private-link order binds to the account.

### Email magic-link sign-in (operator: magic link)
- **D-05:** `POST /api/v1/public/nostr/email/request` — accepts `{email}` (+ `?shop=`), always returns the same "check your email" body (no-oracle — codebase convention, not negotiable). Token is high-entropy, single-use, ~15 min TTL; hash-only persistence (mirror `nostr_challenges`).
- **D-06:** Rate-limit per email + per IP (email-bombing) via the existing `rate_limit_buckets`/`check_public_rate_limit` machinery; tighter than sign-in (e.g. 3/email/hr, 10/IP/min).
- **D-07:** Send via the existing `email_queue` worker — host readiness check `settings.is_email_notifications_configured()` already gates it; magic-link row should carry a clear skip reason like the existing `host-email-unconfigured`.
- **D-08:** Clicking the link (`GET /infinitemarkets/auth/email#<token>` or query — planner picks the least-leaky option consistent with the §5.4 fragment-token contract) verifies + mints the session cookie (same HttpOnly/Secure/SameSite=Strict cookie, same 7-day TTL).

### Order auto-binding (operator: auto-bind on verify)
- **D-09:** On successful email verification, orders with matching `buyer_email_hash` (same merchant) attach to the account — including unclaimed ones. Surface a quiet "we found N past orders" note on the orders page (honest UX, not silent magic).

### Identity linking / merge (operator: prove both, union merge)
- **D-10:** Signed-in account can add the other identity: email → sends a verify link to that email (same token machinery, flag "link-only: prove, don't sign-in"); nostr → NIP-07 challenge round-trip (existing `nostr/challenge`+`verify` pattern, link variant).
- **D-11:** If the verified identity already belongs to another account → union merge: identities and order bindings move to the surviving account, sessions re-point, the other row is retired. Either direction is legal.

### Profile page (operator: email + link-nostr card)
- **D-12:** Email-only accounts see verified email, order prefs, and a "Link a Nostr key" card; the kind-0 editor unlocks once a nostr identity is linked. Nostr accounts get a symmetric "link an email" action.

### UI surface
- **D-13:** Sign-in modal offers both methods: "Sign in with Nostr" (existing flow) + "Email me a sign-in link" (email field + submit). The modal/chip/orders/profile surfaces from this session are the baseline — extend, don't rebuild.

### Posture locked by codebase convention (not questions)
- No-oracle responses everywhere (uniform "check your email" regardless of account existence).
- Encrypted-at-rest PII (email stored `*_enc` like `contact_enc`; HMAC indexes for lookups).
- Exact-Origin + CSRF on mutations; session cookie flags unchanged.
- Bound every user-supplied string; bound email send volume.

</decisions>

<specifics>
## Specific Ideas

- Deployment fact: this host has working SMTP (Fastmail via `lnbits_email_notifications_*` admin settings) — but the feature MUST degrade honestly when unconfigured (`host-email-unconfigured` skip + UI hint), not silently no-op.
- `INFINITEMARKETS_NSEC_SIGNIN` (added this session, env-gated, currently on) is the precedent for "dev affordance behind a flag" — magic-link needs no flag but the same restraint applies.
- Orders' contact email lives inside `contact_enc` JSON — backfill decrypts it; new checkouts write `buyer_email_hash` at order creation.

</specifics>
