# Phase 4 Plan Review — Direct Source-Grounded Review

This is a direct review by the current model, **not** an independent cross-AI review. Claude and Codex CLIs could not authenticate, so there is no cross-review consensus. The existing plans are not ready for execution unchanged.

## Summary and risk

**HIGH risk.** The intended import-only scope and single-writer stock accounting are sound, but several plan assumptions contradict the current schema and workflow, and the proposed cutover can release or expose stock while old invoices remain payable. The concurrency test as written cannot exercise the claimed race when the freeze guard is active.

## Strengths

- The draft-first design is supported by the existing no-publication/no-checkout gates: `_enqueue_product` returns for drafts (`infinitemarkets/services/catalog.py:279-291`) and `_assert_purchasable` rejects them (`infinitemarkets/services/checkout.py:293-303`). Binding decision: `04-CONTEXT.md:23-25`.
- Reusing conditional stock updates is appropriate: `begin_saga` atomically increments `stock_reserved` only when capacity remains (`infinitemarkets/services/checkout.py:1060-1103`), and the DB checks `stock_reserved <= stock_on_hand` (`infinitemarkets/migrations.py:158-160`). Planned in `04-02-PLAN.md:31-32`.
- The merchant keystore has an event-signing API without exporting a private key (`infinitemarkets/keystore.py:201-208`), although the plan must specify a supported event/signature format (`04-01-PLAN.md:33,159-163`).

## Concerns — address before execution

1. **HIGH — Flat, uncategorized products cannot use today's create/publish path.** `products.catalog_id` was created `NOT NULL` and renamed to `category_id`; `Product.category_id` is required and `create_product` explicitly requires an existing category. Storefront and public API both inner-join categories. Thus `04-01`'s "uncategorized drafts through normal create" cannot run, and the research assertion that category is nullable is incorrect. Either revise D-03 explicitly to use a dedicated neutral *imported* category (not stall→category mapping), or plan a comprehensive nullable-category schema/service/publication/UI change before import. Do not silently change a binding user decision. Evidence: `infinitemarkets/migrations.py:113-119,1234-1239`; `infinitemarkets/models.py:65-69`; `infinitemarkets/services/catalog.py:823-833`; `infinitemarkets/views.py:359-368`; `infinitemarkets/views_public_api.py:108-117`. Plans: `04-CONTEXT.md:30-33`, `04-RESEARCH.md:15-16`, `04-01-PLAN.md:30-32,159-163`.

2. **HIGH — Freezing the new catalog does not freeze the *old* order intake or prove the legacy liability snapshot is complete.** `04-02` only proposes an Infinite Markets cutover row and checkout guard. nostrmarket still accepts order DMs when `merchant.config.active` is true, and has its own authenticated merchant toggle; an uploaded optional liabilities section cannot prove no additional invoices appeared after the snapshot. A safe boundary needs a documented, verified external old-intake disable, an authoritative/payable invoice inventory snapshot with provenance, a reconciliation window, and fail-closed confirmation *before* enabling imported sales. Do not imply toggling the new extension has frozen the old one. Evidence: `/home/exedev/lnbits/lnbits/extensions/nostrmarket/services.py:483-493,99-129`; `/home/exedev/lnbits/lnbits/extensions/nostrmarket/views_api.py:246-259`; `/home/exedev/lnbits/lnbits/extensions/nostrmarket/migrations.py:75-94`. Plans: `04-01-PLAN.md:34,159-163,168-176`, `04-02-PLAN.md:27-35,130-146`; requirement `.planning/REQUIREMENTS.md:74-75`.

3. **HIGH — Local cancel/expiry/abort are not proof an old invoice is unpayable.** `resolve(..., cancel)` only changes the new DB; the plan contains no call or evidence that the legacy Lightning invoice can no longer settle. `abort()` releases all partitions and returns to `none`, while the same imported product may already have been published; a still-payable invoice and a new buyer can claim one unit. Auto-expiring holds by a merchant-provided `payable_until` without verified wallet/invoice status has the same risk. Existing Infinite Markets deliberately treats late settlement as a payment exception, not stock consumption, but cannot apply that policy to nostrmarket invoices without reconciliation. Define settlement/expiry/cancel evidence per legacy invoice, durable liability retention, fail-closed abort (imported products remain unavailable unless old intake and outstanding liabilities are safe), and stock consumption on legacy payment rather than simply releasing the partition. Evidence: `infinitemarkets/services/settlement.py:280-288,323-328,344-368`; legacy invoice hash in `/home/exedev/lnbits/lnbits/extensions/nostrmarket/services.py:109-129`. Plans: `04-CONTEXT.md:45-54`, `04-02-PLAN.md:31-34,130-146`; `.planning/REQUIREMENTS.md:74-75`.

4. **HIGH — The completion gate excludes partitioned liabilities and publication bypasses it.** `04-02` checks only `state='open'`, yet partition moves a *still-payable* liability to `partitioned`. The proposed per-product unblock and `complete` would then permit checkout without a permanent protected allocation/settlement rule. Separately the existing bulk `publish` flips `draft = false` and enqueues publication, and merchant-wide publish enumerates products without a cutover filter. Import drafts can therefore be published before any freeze; Nostr publication can advertise stock before cutover even if the checkout guard refuses orders. Require an explicit gate on publish, visibility, stock projection, both web and Gamma intake, and a completion predicate that accounts for payable partitioned quantities (or irrevocably reserves them until proven resolved). Evidence: `infinitemarkets/services/catalog.py:1172-1175,279-305`; `infinitemarkets/services/merchant.py:458-494`; `infinitemarkets/services/checkout.py:233-269,1438-1492`. Plans: `04-01-PLAN.md:30-35`, `04-02-PLAN.md:33-34,43-45,53-66,139-146`.

5. **HIGH — The planned scarce-stock race test is unreachable under the proposed guard.** `04-02` refuses checkout on imported products in `frozen|reconciling`; `04-03` tries to race that checkout against partition of a liability on the same product. With the guard active the buyer loses before the reservation update, so the test passes even if the allocation lock is removed. With it inactive the plan has no reason why partition is allowed and the imported product is publishable. Split into (a) guard test for both web and Gamma and (b) a narrowly constructed real-transaction contention test where both stock writes are actually reachable, with synchronization/barrier and asserted attempted statements; run on SQLite and PostgreSQL. Evidence: `infinitemarkets/services/checkout.py:233-269,1060-1103,1438-1492`; `infinitemarkets/db.py:104-140`. Plans: `04-02-PLAN.md:139-146`, `04-03-PLAN.md:25-29,93-105`.

6. **MEDIUM — The reservation row cannot be reused without schema changes; merely copying accounting isn't enough.** `inventory_reservations.order_id` is `NOT NULL` with an FK to an Infinite Markets order and `UNIQUE(order_id, product_id)`; a legacy liability is not such an order. Existing release/consume queries are keyed to order_id and only process `state='held'`. Favor a distinct `liability_partitions` table with unique liability ID and a shared conditional `stock_reserved` update in the same transaction; specify idempotent consume/release and reconciliation semantics explicitly. Evidence: `infinitemarkets/migrations.py:630-645`; `infinitemarkets/services/orders.py:286-320`; `infinitemarkets/services/settlement.py:344-368`; `infinitemarkets/services/checkout.py:1068-1103`. Plans: `04-02-PLAN.md:31-32,46-50,119-137`.

7. **MEDIUM — Import execution and dedup are underspecified for safety.** The existing `create_product` owns its own transaction and enqueues an intent unless draft, while the plan requests wrapping it in a single `DomainTransaction`. Existing `patch_product` republishes and adjusts status; updating a previously published product on re-import could silently change stock and publicity, even with matching legacy ID. Merchant-wide uniqueness by `legacy_id` also conflates two sources with identical IDs. Define a transaction-aware catalog primitive for imported *drafts*, source-namespaced identity, hard refusal to overwrite published/reserved products, upload-content immutability between preview and execute, and atomic idempotent retry. Evidence: `infinitemarkets/services/catalog.py:823-894,975-1025,1039-1063`; plans: `04-01-PLAN.md:30-34,135-163`.

8. **MEDIUM — Source format, units, and secret custody need an explicit contract.** nostrmarket uses `products.price REAL`, `quantity INTEGER` and `orders.invoice_id` / JSON `order_items`; Infinite Markets expects validated integer `amount_minor`, `currency_decimals`, and stock. The research text claims an order `invoice` field not present in the local table. Define exact uploaded order/line-item provenance, payable status checking, Decimal conversion and currency/rounding rules, CSV multi-row variant/image handling, neutral notes vs freeform payload persistence, and bounded sensitive-data retention; do not store or return raw uploaded secrets in `import_rows.payload_json` or a manifest. The available keystore signs `UnsignedEvent`, not arbitrary JSON: define an unambiguous signed commitment/event kind and verifier, or use the discretion in CONTEXT to choose a hash-only audit record if signing has no safe format. Evidence: `/home/exedev/lnbits/lnbits/extensions/nostrmarket/migrations.py:40-57,75-94`; `infinitemarkets/services/catalog.py:534-596`; `infinitemarkets/keystore.py:201-208`. Plans: `04-RESEARCH.md:36-40`, `04-01-PLAN.md:29,33-34,47-48,135-163`.

9. **LOW — The context source-kind labels are off by one.** `04-CONTEXT.md:34-36` says stall=30018/product=30019; actual nostrmarket emits stall=30017 and product=30018, which the plan/research correctly use. Fix the context typo before implementation to avoid ambiguous fixtures. Evidence: `/home/exedev/lnbits/lnbits/extensions/nostrmarket/models.py:178,258`; `04-RESEARCH.md:23-29`; `04-01-PLAN.md:119-122`.

## Suggested replan order

1. Resolve the product/category contradiction with the user; correct source-kind labels and incorrect research assumption.
2. Define the external legacy freeze/snapshot proof and liability evidence/state machine, including cancel, settle, late-pay, expiry, partition and abort. Keep old payable stock protected until authority confirms it is safe.
3. Specify one transactional stock primitive and lock/order discipline for new reservations and legacy partitions; gate publishing and both checkout rails on cutover state *inside* the authoritative write transaction.
4. Redesign the rehearsal into a freeze-guard test plus a separate genuinely reachable concurrent allocation test for both supported DB backends; prove that removing the stock guard makes the latter fail.
5. Tighten import data normalization, signature format, dedup/retry, upload immutability and privacy before task execution.
