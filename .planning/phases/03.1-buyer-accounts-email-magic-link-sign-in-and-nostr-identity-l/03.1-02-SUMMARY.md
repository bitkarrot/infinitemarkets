# 03.1-02 Execution Summary

## What Was Built

**Task 1 — magic-link transport (`email.py`):** `enqueue_magic_link` inserts
orderless `channel='account'`/`event_type='signin_link'` rows inside the
caller's tx with the raw token AEAD'd into `payload_enc` (record_id = the queue
row). The worker renders subject/body at send time — the link is
`{public_base_url}/infinitemarkets/auth/email?shop=<pubkey>#<token>` — honors
`email-disabled`/`host-email-unconfigured`/`merchant-inactive` suppression
verbatim (consent suppression skipped by construction), consumes an
`email-account` per-recipient bucket (8/hr), and wipes `recipient_enc` +
`payload_enc` together on sent. The token never reaches subject, body (other
than inside the fragment), or logs.

**Task 2 — sign-in vertical:** `request_email_signin` runs the per-email
bucket, resolves/creates the identity's account (request time is the only
moment plaintext email exists), mints the hash-only token row and enqueues
the queue row in one tx. `verify_email_token` strict-decodes, merchant-scopes,
CAS-consumes, then mints the identical session (account pubkey/email compat
fields populated) and counts `buyer_email_hash`-bound orders. Public routes
`_guard` + per-IP bucket + `require_origin`; request returns the uniform
`{"sent": true, "detail": "check your email for a sign-in link"}` for every
outcome; verify maps every failure to the identical 401. `GET /auth/email`
serves the fragment landing; `public_auth_email.js` consumes only
`GM.orderToken()` (storefront owns capture/strip), keeps its own
`api()`/`shopQuery()` mirrors, all DOM via `GM.h`. `/nostr/challenge`
additionally discloses `email_signin` (host SMTP + ext flag) and
`nostr_signin` (merchant inbox active) alongside `nsec_signin`.

**Task 3 — identity linking + union merge:** `POST /nostr/link/email` binds a
`purpose='link'` token to the session account (early 409 when it already holds
an email); `GET /nostr/link/challenge` + `POST /nostr/link/verify` reuse the
kind-22242 round-trip on `purpose='link'`/`account_id`-scoped rows —
`_materialize_account` lazily resolves legacy `account_id IS NULL` sessions
inside the link tx. `resolve_verified_email`/`resolve_verified_pubkey` share
`_resolve_verified`: unowned → attach (CAS); owned-by-target → idempotent;
owned-elsewhere → union merge iff representable (each of email/pubkey at most
one distinct value), else `MERGE_CONFLICT` 409. Merge moves every movable
identity (`*_enc` re-encrypted under the survivor AAD), retires the loser
first inside the tx to release partial-unique slots, then re-points sessions,
link tokens, and link challenges — all atomic. `verify_signin` now SELECTs
`purpose='signin'`; `SESSION_INVALID` copy is method-neutral. Spec §5.4 grew
the six routes; §4.7/§4.18/§4.21/§4.22/§4.23 document `buyer_email_hash`, the
account channel + `payload_enc`, and the new tables. Registry gained the six
routes + the three pre-existing 03-03 drift rows (`GET /profile`,
`GET|POST /public/nostr/profile`), `GET /orders` carries a dual-use comment,
and `TABLE_CLASSIFICATION` gained `buyer_accounts`/`email_signin_tokens`
(NOT_MODELED).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 2 - Missing critical] Merge write ordering vs partial-unique index**
- **Found during:** Task 3 runtime testing (3 link/merge tests failed with
  `UNIQUE constraint failed: buyer_accounts.merchant_id, buyer_accounts.*_hash`).
- **Issue:** The plan's "write the union onto the survivor, retire the loser"
  ordering trips the m008 partial-unique index — the moved hash exists on the
  not-yet-retired loser when the survivor UPDATE runs.
- **Fix:** The loser retires FIRST inside the same tx (cleared identities +
  `retired_at`), then the survivor CAS-UPDATE lands the moved hashes, then
  session/token/challenge re-points. A `MERGE_CONFLICT` rollback still
  restores everything — atomicity unchanged.
- **Files modified:** `infinitemarkets/services/nostr_auth.py`
- **Verification:** `test_union_merge_*`, `test_link_token_repointed_*` green.
- **Committed in:** `0fbf23a`

**2. [Rule 2 - Missing critical] `email_enc` custody for link requests**
- **Found during:** Task 3 design — `resolve_verified_email` receives only the
  hash (the queue row wipes recipient material on send), so a naive attach
  would leave linked emails permanently display-less (`email_enc` NULL).
- **Fix:** `request_email_link` resolves/creates the identity's owner account
  at request time (same `_get_or_create_account(email=...)` the signin path
  uses) while the plaintext is in hand; an unattached email therefore merges
  its singleton holder — `linked: true, merged: true` is the honest result —
  and `email_enc` lands on the survivor under its own AAD.
- **Files modified:** `infinitemarkets/services/nostr_auth.py`
- **Verification:** `test_link_email_from_nostr_session` asserts the profile
  returns the linked email; `test_union_merge_*` asserts `email_enc` moved.
- **Committed in:** `0fbf23a`

**3. [Rule 2 - Missing critical] Resolve/merge seam landed in Task-2 commit**
- **Issue:** `verify_email_token`'s `purpose='link'` branch calls
  `resolve_verified_email`; the plan assigns the resolvers to Task 3, but the

- **Fix:** `resolve_verified_email`/`resolve_verified_pubkey`,
  `_resolve_verified`, `_merge_accounts`, `_bound_orders`, `_link_target`

- **Committed in:** `66309fd`, `0fbf23a`
